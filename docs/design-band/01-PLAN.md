## Решения, которые больше не переоткрываем

1. **Перегенерируемое ≠ аннотируемое.** Два класса артефакта, повышение — явный акт человека.
   Практическая граница = включение нумерованных выносок.
2. **Модель никогда не правит наш SVG напрямую.** Правка сырого SVG моделью — 2.35% полного успеха
   против 99.8% у структурированного формата. Модель выдаёт структуру, приложение детерминированно
   рендерит. Это же даёт стабильные id: их минтит рендерер.
3. **Ничто сгенерированное не пишется сервером в карточку.** Кандидат → клиент применяет в форму →
   человек сохраняет обычным путём. Серверный отказ по `frozen` в момент применения.
4. **Подтверждение решения = обычная правка обычного поля.** Запись решения — провенанс, не источник
   печати. Sign-off остаётся единственным механизмом одобрения.
5. **Стежок принадлежит операции.** Штрих несёт `operation_ref`, вид выводится из полей операции.
6. **Ткань и цвет рендера — из BOM-статей и колорвеев**, не свободным текстом.
7. **3D не генерируем.** `.glb` от конструктора + `<model-viewer>`.
8. **Никакой отдельной вкладки «AI».** Действие живёт рядом с артефактом, который оно меняет.

## Информационная архитектура: что проверяет прототип

Единственное, где критики разошлись. Оба согласны, что AI — действие, а не вкладка; спорят о том,
переезжает ли `concept`/`details` с HEADER в отдельную вкладку.

**Вариант A — три вкладки как сейчас, содержимое переразложено**
`header` (идентификация, классификация, роли, **concept + details остаются здесь**) ·
`moodboard` → **references** (сырые картинки, роли, подписи) ·
`sketch` → **flats** (рабочие справки, принятые листы, выноски, SVG-рейс)

**Вариант B — Brief / References / Flats**
`brief` (идентичность + concept + аспекты описания конструкции, **вынуто из header**) ·
`references` · `flats`. Остальное из header уезжает в отдельную вкладку идентификации или остаётся.

Факты для решения (все проверены):
* `sketch` и `moodboard` — один компонент, обе смонтированы одновременно, делят один массив
  `callouts` и одну историю отката;
* нумерация выносок по-листовая и **асимметричная**: `referencedNumbers()` возвращает `[]` для
  мудборда. Слить листы = схлопнуть два пространства номеров, из которых сервер выводит имя детали кроя;
* `notes` пишется из ДВУХ вкладок сразу (header и moodboard) — это надо развести в любом варианте;
* `caption` есть в схеме и БД, UI нет нигде;
* снаружи в дизайн-бэнд никто не диплинкует (только `?tab=samples`) — перестановка дешёвая;
* `IDEA_TABS` хардкодит `['header','sketch','moodboard','samples','history']`;
* удаление вкладки — решённый приём через `FOLDED_TABS`, старая ссылка продолжает работать;
* **добавление/удаление поля из проекции дайджеста — не дешёвое**: протухает каждая подписанная
  карточка в базе разом. Переносить контент между вкладками бесплатно, менять состав проекции — нет.

## Фазы

### Ф0 — Гигиена, до всякого AI (несколько дней, чистый выигрыш)

Эти вещи нужны независимо от того, поедет ли генерация вообще.

* **Ф0.1** Починить дыру `SECTION_WATCH_FIELDS`: клиентский пред-сейв для DESIGN не содержит
  `concept`, серверная проекция содержит (`signoffs-field.tsx:50` против
  `techcard_section_digest.go:272`). Сегодня редко ловится; автозаполнение concept сделает это
  регулярным, и экран не предупредит.
* **Ф0.2** UI для `TechCardMediaItem.caption` на плитке медиа. Поле есть на проводе и в БД,
  подписано `// carried (v2; no UI yet)`. Это и есть «описание к каждой фотке» из замысла.
* **Ф0.3** Значение энума `TECH_CARD_MEDIA_KIND_SIDE`. Единственная реальная дыра в ролях картинок.
* **Ф0.4** Развести `notes`: сейчас одна строка редактируется с двух вкладок.
* **Ф0.5** Профиль экспорта SVG в `renderLayoutSvg` (писатель уже есть, ноль вызовов):
  `<defs>` первым · id в алфавите `[A-Za-z][A-Za-z0-9-]*` · презентационные атрибуты вместо
  `<style>` · пунктир ≤6 значений · ноль `<marker>` · ноль `vector-effect` · ноль `pathLength`.
  Плюс письменная инструкция дизайнеру по настройкам Illustrator (см. §13.3 критики).

### Ф1 — Честный MVP генерации (4–6 недель)

* **Ф1.1 Инфраструктура заданий.** Таблица `generation_job` + 13-й тикер-воркер, скопированный с
  `internal/mail/worker.go` (тикер + `context.WithTimeout` + `saferun.Recover` + бэкофф 30 с → 5 мин
  + `health.Reporter`); `send_email_request` — работающий образец claim-and-mark аутбокса.
  Клейм коротким отдельным стейтментом, не внутри длинной транзакции (пишущие SERIALIZABLE).
  Писать `total_cost` из OpenRouter `/generation` в строку задания, месячный жёсткий потолок рядом
  с проверкой, не в прозе. Переиспользовать `internal/circuitbreaker`. Различать «модель отказала»
  (не ретраить) и «провайдер 503» (ретраить). **3–5 дней.**
* **Ф1.2 Мультимодальный вход.** Сегодня `chatMessage.Content` в Go — простая строка; картинку
  послать нельзя. Это новая работа, и она блокирует всё остальное в Ф1.
* **Ф1.3 «Generate flat».** Вход — размеченные медиа (роль + `caption`) + `concept`.
  Выход — **растровый** флэт обычной строкой медиа, неизменяемой, версионированной, в классе
  **рабочая справка**. Nano Banana Pro ~$0.13 или Nano Banana 2 ~$0.067.
  Промпты владельца (3 вида / отдельная деталь) берутся дословно, они хорошие.
* **Ф1.4 Повышение до принятого листа.** Явная кнопка. До неё — перегенерации сколько угодно и
  только приватные ненумерованные заметки; после — неизменяемо, выноски, печать, дайджест DESIGN.
* **Ф1.5 Аннотирование СУЩЕСТВУЮЩЕЙ поверхностью.** Ноль новых систем координат, ноль нового
  редактора. Выноски прикалываются к новому `media_id` и не могут съехать: медиа append-only.
* **Ф1.6 Автозаполнение `concept` / `details`** на существующем синхронном эндпоинте, как кандидат
  с диффом, который человек применяет и сохраняет. После Ф0.1.
* **Ф1.7 Спайк на вечер, параллельно и сразу:** Recraft V4.1 Pro Vector на OpenRouter ($0.30, ~15 с,
  выход SVG) + собрать Recraft `/styles` ($0.005) из картинок, уже лежащих в карточках. Решает,
  жизнеспособен ли нативный вектор. Если да — **«скачать SVG»** как экспорт, а не как редактируемый
  объект в приложении.

**Явно НЕ в Ф1:** векторный редактор, кисти-стежки, тканевый рендер, 3D, параметрическая библиотека.

### Ф2 — Решается по факту использования Ф1

Если сгенерированные флэты реально повышают и аннотируют — идти в вектор. Если посмотрели один раз и
забыли — ответ получен, и редактор не построен.

* **Ф2.1 Структурированный промежуточный формат** (схема из §2 фисибилити: block, fit, symmetry,
  views, params, features, **edges с `seam_class` и nullable `operation_ref`**). Модель заполняет,
  приложение рендерит SVG. Урок NGL/ChatGarment: **чем меньше схема, тем выше надёжность**
  (900 → 350 токенов дало стабильность).
* **Ф2.2 Связь «операция ↔ ребро».** Сегодня `tech_card_operation_piece` — целые детали, никогда
  рёбра. Самая ценная новая связь во всей системе: она же даёт проверку покрытия и питает Ф2.3.
* **Ф2.3 Узкие оверлеи стежков**, привязанные к операциям. Пунктир ≤6 значений живой обводкой;
  всё сложнее — запечённая ресэмплированная геометрия в отдельном одноразовом слое, который на
  импорте перегенерируется, а не парсится обратно.
* **Ф2.4 Круглый рейс SVG** по контракту Ф0.5 + серверный сайдкар по id + обязательный дифф
  «сколько id потеряно / добавлено / задублировано» на возврате.

### Ф3 — Тканевый рендер (только после Ф2, и с честными оговорками)

Два этапа, разные модели, потому что одношаговое «флэт → фотореал» не держит геометрию
(sketch-following: GPT Image 2 — 34/100, Nano Banana 2 — 22/100).

1. Геометрия — настоящий control-адаптер: Z-Image Turbo + Fun-Controlnet-Union-2.1 (Apache-2.0,
   MLSD + canny под прямые швы, $0.0065/MP) или Bria FIBO `sketch_to_colored_image` ($0.04,
   лицензированные данные).
2. Материал и свет — нативная edit-модель со свотчем референсом.
3. Колорвеи — Ideogram `colorways` (hex на маску) / `material-swap`.

Ткань и цвет **только из BOM-статей и колорвеев**. Рендер — иллюстративное медиа: никаких выносок,
не в релиз-готовности, не в фабричном паке. Драпировку не обещать вовсе.

### Ф4 — Решения (после Ф1, независимо от Ф2/Ф3)

Не новый экран поверх старых, а **федерация** с ярлыками авторитета:
серверное требование готовности · детерминированная машинная проверка · вопрос модели ·
отслеживаемое человеческое решение · опциональное предложение.

Реально новое — только **PROPOSED ASSUMPTIONS и SUGGESTED PROPOSALS** с долговечным состоянием
(сегодня dismissal живёт в `sessionStorage`). Две оси вместо пяти корзин:
тип (conflict | assumption | proposal) × состояние (open | accepted | rejected | superseded) +
производное `stale` по дайджесту основания. **Дайджест секции слишком груб** — правка BOM не должна
инвалидировать решение про воротник; нужен пофактовый.

Корзину назвать **Accepted decisions**, не CONFIRMED: «approved» в продукте уже занято sign-off'ом.

### Ф5 — То, чего в брифе нет, а ценность выше (можно начинать параллельно)

Порядок по ценность/усилие:

1. **POM-таблица из DXF + проверка градации.** Без AI вообще. Есть геометрия по размерам, есть
   примитив `dim` — двухточечный замер. Детерминированно, проверяемо, фабрично-обращено.
2. **Канонический PDF релиза (Ф7 из плана печати).** У замороженного релиза должен быть замороженный
   документ с хешем. Ценнее рендеров и 3D вместе взятых.
3. **`.glb` вьюер + попросить файл у конструктора.** `three` уже в зависимостях,
   `<model-viewer>` 72 КБ. **2–3 дня, настоящая сшитая вещь.** Ловушка: `doubleSided` в glTF по
   умолчанию `false` — изнанка через горловину отрендерится дырами.
4. **Стабильная идентичность выноски.** Неизменяемый ключ, номер как представление. До миграции —
   серверный отчёт о зависимостях перед удалением/перенумерацией/заменой медиа.
5. **Предпросмотр последствий сохранения**: какие подписи протухнут, какие выноски сбросятся, кто
   ссылается на затронутые номера.
6. **Критика списка операций** вместо генерации — против известной проблемы (79% прод-операций
   неразличимы).

## Что строит прототип

Статичные экраны, по два варианта, полоса выбора внизу — как делали с медиа
(`tmp/media-new/`, сборка из `parts/`, гейт `qa.mjs`).

| # | Экран | Вариант A | Вариант B |
|---|---|---|---|
| 1 | Каркас дизайн-бэнда | header / references / flats | brief / references / flats |
| 2 | References | сетка с ролью и подписью на плитке | лента по ролям, подпись в панели |
| 3 | Запуск генерации | инлайн-панель в пустом состоянии flats | модалка с предпросмотром входов |
| 4 | Рабочая справка (кандидат) | стопка версий, одна активна | ряд кандидатов рядом |
| 5 | Повышение до листа | кнопка + разбор последствий | шаг подтверждения с чек-листом |
| 6 | Принятый лист с выносками | нынешняя галерея, причёсанная | лист во всю ширину + легенда сбоку |
| 7 | Concept / details как кандидат | дифф по полям | построчное принятие |
| 8 | Decisions | федерация с ярлыками авторитета | две оси: тип × состояние |

Гейт прототипа тот же, что был: playwright из npx-кэша — ошибки JS, горизонтальный вылет на 1440 и
900, покрытие моно-шрифта (выпадают `⧉ ⤢ ⠿ ⟲ ⎘ ⌗ ⋮ ⣿ ⊹`, живут `❐ ↗ ┋ ≡ ✓ ✕ × · ▸ ▾ ↺ ⇅ ‹ › ⊞ ⌘`).
