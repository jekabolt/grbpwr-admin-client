# 06 — Гэпы данных: прототип против реального бэкенда

Дип-ревью линзой данных (2026-08-29). Прототип: `tmp/design-band/proto.html`
(состояние — `proto/src/20-state.js`). Бэкенд: `grbpwr-products-manager` (пути ниже — от корня
этого репо). Всё процитированное проверено по коду этого прохода; помеченного «предположение» нет —
что не удалось доказать, названо в §4 «где искал и не нашёл».

Точка опоры, которую надо держать в голове на каждой строке: `UpdateTechCard` — это
DELETE + INSERT по тринадцати таблицам (`internal/store/techcard/techcard.go:515-528`), и
**в том же самом файле уже стоят все три исключения из этого правила**: append-only ребёнок,
которого сейв не трогает (`tech_card_revision`, `techcard.go:495-497`), keyed-upsert по
`line_key` (BOM и детали, комментарий `techcard.go:489-494`) и presence-aware секции.
Новым таблицам полосы DESIGN не нужен новый механизм — нужен выбор правильного из трёх.

## 1. Находки

### Г1. Генеративного конвейера на сервере не существует — вообще ничего

- **Что не сойдётся:** прототип стоит на `runs[]` (задание → статус → выход → цена), а на сервере
  нет ни клиента генерации картинок, ни таблицы заданий, ни строки результата, ни профилей.
- **Доказательство:** `internal/openrouter/openrouter.go` — только chat completions
  (`GenerateOperations` :380, `Complete` :414, `chat` :434), картинок не умеет; синхронный
  `http.Client{Timeout}` 60 с (:34-35, :95). Поиск `generation|_job|queue` по
  `internal/store/sql/` даёт только email-ретраи (0048) и диспатч кампаний (0208).
- **Что это значит:** новая подсистема целиком — `design_run` (профиль@версия, params, снимок
  входов JSON, автор, цена, статус, provider_request_id, client_request_id UNIQUE) +
  `design_run_output` (media_id, ghost-вид, hidden_at, derived_from) + провайдер-клиент + воркер.
  Образец воркера уже в репо: `email_campaign_recipient` (0208) — status/attempt_count/
  next_attempt_at/claim_expires — готовая машина «claim → attempt → retry».
- **Тяжесть: блокирует** — это сама фича.

### Г2. Поимённо: что full-replace уничтожит, если положить в документ

- **Что не сойдётся:** из формы состояния прототипа документ переживают только: `card.*` (колонки
  `tech_card`), `garmentNote`/`concept.text` (`tech_card.concept`, 0071:13), `aspects`
  (`tech_card_detail`, 0079:45-54), `refs`/`moodboard` (`tech_card_media` — с оговоркой Г10),
  выноски листа (`tech_card_callout` — с оговоркой Г4), `colorways` (персистентные, не ребёнок
  карточки — `techcard.go:487-488`). **Всё остальное документ сотрёт первым же сейвом
  неосведомлённого клиента:** `runs` и их `inputs`-снимки, `batches` (пачки загрузок), `pictures`
  (лента/полка, `hidden`, `mixedInput`, `derivedFrom`), `slots` + штампы автора, `detailSeq`,
  `sheet.revs` (составы версий, `mixedConsent`), `journal` (минты/печати), `calloutSeq`,
  `budget.spent`, рецепты палитры, `moodDraft`/`concept.sugs`.
- **Доказательство:** список DELETE — `techcard.go:515-528`; прецедент потери —
  `internal/dto/techcard.go` (комментарий «16 деталей из 18 на бете несли Detached», цитирован в
  02-DECISIONS A1).
- **Что это значит:** каждой строке выше — либо своя таблица по образцу `tech_card_revision`
  (ключ `tech_card_id`, сейв не трогает), либо честная смерть. **Правда должны пережить:** прогоны
  с ценами и снимками входов, пачки, лента с hidden, слоты со штампами, версии листа, журнал
  выдач, дневной расход, рецепты палитры. **Не должны:** `moodDraft` и неакцептованные
  `concept.sugs` (сессионный черновик — принятое уже легло в `concept.text`), `ui.*`,
  `detailSeq`/номера промпта (derived).
- **Тяжесть: блокирует** (архитектурная граница всей фичи), но механизм готов — см. шапку.

### Г3. Минт vN НЕ может ехать на tech_card_release — H0 верен как образец, не как дом

- **Что не сойдётся:** H1 минтит версию первой выноской. Релиз же (а) гейтится readiness
  (`internal/apisrv/admin/techcard_readiness.go:30`, стор `readiness.go:97` — карточка на стадии
  дизайна не пройдёт эти гейты никогда), (б) замораживает ВСЮ карточку до re-open в draft
  (`ErrTechCardReleased`, `techcard.go:323`) — дизайнер после первой выноски не смог бы
  продолжить, (в) снапшотит весь документ (0096: JSON всего TechCard).
- **Доказательство:** `0096_economics_wave3_techcard_release.sql`,
  `0162_tech_card_release_number_and_revision_journal.sql` (release_number = MAX+1 + UNIQUE).
- **Что это значит:** новая таблица `design_sheet_version` (tech_card_id, sheet_number MAX+1 +
  UNIQUE — дословно приём 0162, состав JSON: слоты → media_id + content-идентичность, by, time,
  mixed_consent). Дайджест DESIGN читает последнюю строку отсюда (H2), релиз карточки остаётся
  своей осью (K: `Rev.N` ≠ `vN`).
- **Тяжесть: блокирует** проектирование контракта.

### Г4. Номер выноски: сервер не минтит, не хранит счётчик и не требует уникальности

- **Что не сойдётся:** Р9 «номер минтится один раз, после удаления — дыра, переиспользования
  нет». В схеме `callout_number INT NOT NULL DEFAULT 0` и **ни одного UNIQUE**
  (`0067_add_tech_card_core.sql:110-121`); стор складывает выноски в map по номеру — дубль
  молча схлопывается последним (`materials.go:90`). Клиентский max+1 после удаления верхней
  выноски переиспользует номер, и `tech_card_piece.callout_number` **молча переименует деталь
  кроя** по чужому тексту (`materials.go:100-112` — это не Detached, это хуже).
- **Что это значит:** колонка-счётчик `tech_card.callout_seq` (шапка переживает сейвы) +
  серверный минт номера; ретроактивный UNIQUE невозможен — легаси-нули дублируются, а partial
  index в MySQL нет (при нужде — generated column `NULLIF(callout_number,0)` + UNIQUE).
- **Тяжесть: блокирует** — это ось адресов, ради которой затевался минт.

### Г5. Верстак (slots) не имеет дома, а в документе жить не может

- **Что не сойдётся:** слот меняется «свободно, любым автором» (G1) со штампом (G6.3) и per-slot
  CAS (I8.8). В документе каждый клик слота = полный сейв: CAS по `lock_version`
  (`techcard.go:277-281`, 0071:9) конфликтует с открытой формой коллеги, перезаписывает 13
  таблиц, а «штамп автора» был бы полем, которое клиент присылает сам, — то есть подделкой.
- **Доказательство:** ни F6, ни G/H/I не называют таблицу верстака; в сторе её нет.
- **Что это значит:** таблица `design_bench_slot` вне документа: (tech_card_id, slot_key —
  `front|back|side_l|side_r` или минтуемый `slot_id` детали (H4), media_id, name, set_by,
  set_at, slot_rev для CAS). Пишется отдельным RPC, не сейвом карточки. SERIALIZABLE
  (`store/db.go:63`) делает «прочитал slot_rev → сравнил → записал» честным бесплатно.
- **Тяжесть: блокирует.**

### Г6. Деньги: цены нигде не хранятся, бюджет не имеет владельца, лимитер не деньги

- **Что не сойдётся:** `budget {spent, cap}` и цена на строке прогона. В бэке нет ни одной
  колонки стоимости AI; текущий `openrouter` usage вообще не парсит (grep `usage|cost|tokens`
  по `internal/openrouter/` — пусто; правка к A7, который цитировал строки, которых в master
  нет). `internal/ratelimit` — in-memory, обнуляется рестартом и подключён только к
  frontend/auth (`apisrv/frontend/server.go:36`, `apisrv/auth/auth.go:71`), к admin-AI — нет.
- **Что это значит:** price — колонка `design_run`; «today $X of $2.00» = SUM по дню **внутри
  той же SERIALIZABLE-транзакции, что вставляет строку прогона** (две одновременные вставки под
  потолком сериализуются бесплатно); cap — строка настроек (образец: `workshop_settings`, 0272).
  Открытый вопрос владельцу: cap на организацию / карточку / человека.
- **Тяжесть: учесть при проектировании** — дёшево, но обязано существовать до первого платного
  вызова (E: «платный вызов на нажатие без лимита выносится одним человеком»).

### Г7. Возврат PNG в медиа: verbatim-пути нет, а штатный путь портит флэт

- **Что не сойдётся:** E (Ф1) опирается на `UploadContentImageVerbatim` — **такого RPC не
  существует** (grep по бэку и `grbpwr-proto` — только внутренний GIF-путь `uploadRawImageObj`,
  `internal/bucket/image.go:219-226`). Штатный `UploadContentImage` перекодирует всё в lossy
  WebP: full q100, compressed q60, thumb q90 (`image.go:111,145-167`; форматы входа только
  jpeg/png/webp+gif, `upload.go:20-38`). Чёрная линия 1 px — худший случай lossy; печать 1:1 и
  зум технолога пойдут с деградированного файла, PNG-оригинал не сохраняется.
- **Что это значит:** обобщить raw-путь до PNG (дни: механика вся есть — тот же
  `uploadRawImageObj` с другим декодером заголовка) и решить, какой вариант печатается.
- **Тяжесть: переделка позже, если пропустить** — молчаливая, всплывёт на бумаге.

### Г8. SVG и .ai: приёма нет, санитайзера нет, у media обязателен растровый триплет

- **Что не сойдётся:** J6 «SVG — лучший случай». Сервер SVG не принимает (`decodeImage`:
  jpeg/png/webp; gif отдельно), санитайзера в репо нет, а строка `media` требует NOT NULL
  full/thumbnail/compressed с размерами (`0001_initial_setup.sql:512-525`) — вектор обязан быть
  растеризован сервером, чтобы вообще стать media. Дом для непрозрачного оригинала (.ai, SVG-исходник)
  уже есть — `library_file` (0312: приватный S3, sha256, size_bytes, file_name, uploaded_by), но
  он не связан с `media` ни одним полем.
- **Что это значит:** пайплайн «санитайз → растеризация → media + связь media↔library_file
  (колонка source_file_id)». Это Ф1+, не Ф0.
- **Тяжесть: переделка позже** (вектор можно отложить, двери J6 честно закрыть).

### Г9. content_sha256 у media нет — снимок Rev.N морозить нечем

- **Что не сойдётся:** I8.7 требует «снимок морозит content_sha256», J3 — хеш в провенансе.
  У `media` только три URL + размеры + blur_hash (`0001:512-525`); хеш есть только у
  `library_file` (0312:37).
- **Что это значит:** additive nullable колонка `media.content_sha256` (INSTANT), считать на
  новых загрузках в стриме (приём уже написан в 0312-пути). Бэкфилл истории фиче не нужен —
  версии минтятся только на новых картинках; NULL = «старше фичи», честно.
- **Тяжесть: учесть при проектировании.**

### Г10. Дайджест DESIGN хеширует и мудборд — каждая плитка протухает подпись

- **Что не сойдётся:** полоса делает мудборд зоной высокого оборота (первый пункт процесса,
  двери броска, «одна картинка — два окна»), а `designProjection` кладёт в отпечаток **все**
  строки `tech_card_media`, включая `category='moodboard'`
  (`internal/dto/techcard_section_digest.go:265-278` — digestMedia{MediaID, Kind, Caption, Cat}).
  Добавил референс — подпись DESIGN протухла. Ни один из кругов B–K этого не назвал.
- **Что это значит:** решить ДО контракта: (а) принять как смысл — «подписано всё, что видит
  модель» (тогда полоса обязана показывать причину протухания словами), или (б) вывести
  moodboard-строки из проекции — но это сдвиг отпечатка каждой подписанной карточки с
  moodboard-медиа, то есть осознанная миграция подписи, не правка. Вынуть потом нельзя —
  класс [[digest-write-vs-read-asymmetry]].
- **Тяжесть: блокирует решение о подписи.**

### Г11. Двойной клик GENERATE = двойной платёж: идемпотентности нет

- **Что не сойдётся:** C3 обещает «задание, а не запрос», но в admin-API нет ни одного
  идемпотентного приёма (grep `idempot` — только внутренности accounting); ретрай гейтвея,
  двойной клик и повтор после таймаута — три способа заплатить дважды.
- **Что это значит:** `client_request_id` UNIQUE на строке задания; вставка под SERIALIZABLE
  возвращает существующую строку вместо второй. Плюс правило на частичный ответ: просили 3 вида,
  пришло 2 — строка `done · 2 of 3`, output-строки по факту, цена по факту провайдера.
- **Тяжесть: учесть при проектировании** (дешевле всего на рождении таблицы).

### Г12. Роль 'merch' не существует, 'tech designer' — тоже

- **Что не сойдётся:** `card.roles` прототипа (`20-state.js:60-63`) против
  CHECK `role IN ('designer','constructor','technologist','pattern_maker','grader','approver','other')`
  (`0161_tech_card_role_assignment.sql:25`). Расширение — DROP+ADD CHECK, то есть COPY
  (таблица мала, но правило деплоя одно — [[add-check-is-copy-algorithm]]).
- **Что это значит:** мапить: tech designer → constructor/technologist, merch → 'other',
  или расширять словарь сознательно отдельной миграцией. Прототип правит словарь витрины, не БД.
- **Тяжесть: мелочь, учесть.**

### Г13. У модели нет роста колонкой — пикер 3D требует enriched-чтения

- **Что не сойдётся:** строка пикера «Vera K. · 178 · M» (`20-state.js:96-100`). В `model` нет
  height: рост живёт в `model_measurement` (мм, sparse, `0064:25-32`), размер — в
  `default_sample_size_id` (0064:14).
- **Что это значит:** ListModels уже есть (`admin.proto:910`); чтению пикера нужен рост из
  measurements — вопрос контракта чтения, не схемы.
- **Тяжесть: мелочь.**

### Г14. `fit: oversized` — дыра только в клиентском словаре, не в БД

- **Что не сойдётся / сходится:** H6.7 держит открытым вопрос «расширяем словарь?». В БД
  `tech_card.fit VARCHAR(50) NULL` **без CHECK** (`0139_pr6_style_fields_add.sql:33`) —
  'oversized' легален уже сейчас; заперт только клиентский `FIT_OPTIONS`
  (`style-facts-field.tsx:25`).
- **Что это значит:** ответ владельцу готов — расширение бесплатно, миграции нет.
- **Тяжесть: снимает открытый вопрос.**

### Г15. Мудбордные указания и moodNote: дом есть, но каждый со своей оговоркой

- **Что не сойдётся:** `moodCallouts` без номеров (C2) против `tech_card_callout.callout_number
  NOT NULL` — «без номера» выразимо только легаси-нулём, который Г4 хочет изгнать. Правильный
  дом — приём 0313: JSON-колонка `annotations` на строке связи с картинкой
  (`0313_task_media_annotations.sql`; тот же примитив TechCardAnnotation, те же виды) — то есть
  additive JSON-колонка на `tech_card_media`. `moodNote` — новая nullable-колонка шапки, но
  **только** по verbatim/presence-протоколу (`techcard.proto:829`, :1112 — «absent = сохранить»),
  иначе устаревший бандл сотрёт её молча — ровно класс щитов из раздела D.
- **Тяжесть: учесть при проектировании.**

### Г16. Журнал выдач и QR на бумаге — прецеденты есть, самого журнала нет

- **Что не сойдётся:** H1/H3 требуют журнал («повторная печать пишет строку», «бумага
  самоидентифицируется QR на Rev.N»). Журнала печати не существует нигде в сторе; прецеденты
  ровно этой механики — токены с эпохой у выкроек (`0288_tech_card_pattern_viewer_access.sql`:
  токен минтится лениво, отзывается эпохой) и наряда (`0293_production_run_pack_access.sql`).
- **Что это значит:** append-only `design_sheet_issue` (version_id, действие minted|printed|
  shared, кто, когда) + токен вьюера по образцу 0288, когда дойдёт до публичной ссылки.
- **Тяжесть: учесть при проектировании** (журнал — часть модели минта, лучше родить вместе с Г3).

## 2. УЖЕ ЕСТЬ на бэкенде — брать готовым

Хребет полосы уже построен; круг проектирования экономится на каждом пункте:

1. **Двухклассовая медиа-модель**: `category moodboard|technical` (`0092:44-47`), `kind` со
   значениями reference/swatch (`0073`), `caption` (`0073`). Дубли media_id в двух ролях легальны —
   UNIQUE на (card, media) нет (`0067:98-107`).
2. **Выноски с геометрией**: pos_x/pos_y (`0073`), kind/color/points JSON (`0309`),
   dashed/filled/parts (`0310:36-38`). Клиентская система рисования — восемь видов на четырёх
   экранах (`admin-client src/ui/components/annotation/kinds.ts`).
3. **Имя детали кроя из текста выноски + Detached**: `store/techcard/materials.go:66-114`.
4. **Релизная машина как образец минта**: JSON-снапшот (`0096`), release_number MAX+1 + UNIQUE
   (`0162`), readiness-гейты (`apisrv/admin/techcard_readiness.go:30`,
   `store/techcard/readiness.go:97-104`), заморозка released (`techcard.go:323`).
5. **Три исключения из full-replace в самом сторе**: append-only `tech_card_revision`
   (`techcard.go:495-497`), keyed-upsert BOM/деталей (`techcard.go:489-494`), presence-aware
   секции (`techcard.go:499-513`) + verbatim-протокол на проводе (`techcard.proto:829`, :1112).
6. **Оптимистическая блокировка документа**: `tech_card.lock_version` (`0071:9`) +
   `ErrTechCardConflict` (`techcard.go:277-281`); все пишущие транзакции SERIALIZABLE
   (`store/db.go:63,165`).
7. **Модели**: `model` + `model_measurement` + `model_media` (`0064`/`0065`),
   `tech_card.base_model_id` (`0067:32`), полный CRUD + ListModels (`admin.proto:883-911`).
8. **Словарь цвета** `color{code CHAR(3), name, hex}` (`0130:19-23`) — прототипный DICT
   один в один; пер-продуктовый оттенок — `product.color_hex` (комментарий 0130:6-8).
9. **Colorway с lab-dip жизненным циклом**: hex, pantone, swatch_media_id, round, даты, кто
   решил, причина отказа (`0073`, база 0068). Дыра H6.3/H6.4 — только в клиентском
   `AdminColorwayRef`; чинится additive-полем контракта.
10. **GetMediaUsage** (`apisrv/admin/content.go:158`) — глобальная проверка зависимостей
    media_id перед стиранием байтов (I3, ярус 1).
