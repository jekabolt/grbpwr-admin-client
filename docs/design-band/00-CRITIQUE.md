## 0. ЦЕНТРАЛЬНОЕ ПРОТИВОРЕЧИЕ

Владелец говорит: сгенерированный флэт — **«только для внутреннего понимания»**, на фабрику не идёт.
И тут же: на нём ставятся **нумерованные выноски**.

Это несовместимо, и вот механика, а не мнение:

* `tech-pack-document.tsx:1920` печатает выноски **поверх эскиза в тех-паке**; `:1986` матчит детали
  кроя к выноскам по `calloutNumber`.
* Сервер выводит **имя детали кроя** из выноски, к которой она приколота (`dto/techcard.go`, только
  ТЕХНИЧЕСКИЙ лист).
* `pieces[].calloutNumber`, `operations[].calloutNumber`, `issues[].calloutNumber` — внешние ключи
  на номер выноски.

Значит: **как только на рисунок сел нумерованный колаут, рисунок стал системой координат
фабричной спецификации.** «Внутреннее понимание» описывает качество линии, а не роль артефакта.

### Правило, которое это чинит (три критика сошлись независимо)

Два КЛАССА артефакта, и вещь не может быть обоими сразу:

| | **Рабочая справка** (working reference) | **Принятый лист** (spec plate) |
|---|---|---|
| перегенерируется | да, сколько угодно | нет, никогда |
| нумерованные выноски | **запрещены** | разрешены |
| печатается в тех-паке | нет | да |
| в отпечатке DESIGN | нет | да |
| ссылки из pieces/operations/issues | нет | да |

**Повышение до принятого листа — явный человеческий акт.** Практическая граница = включение
нумерованных выносок. Формула: **перегенерируемое ≠ аннотируемое. Выбирать на артефакт, а не на фичу.**

И одна хорошая новость: **система это уже почти обеспечивает бесплатно.** В бэкенде НЕТ
`ReplaceMedia`/`UpdateMedia` — строки медиа append-only. Значит перегенерация физически рождает новую
строку медиа, а старые выноски остаются на старой картинке. Это правильное поведение. **Не «чинить» его.**

## 1. ЧТО УЖЕ ПОСТРОЕНО И ЧТО ЗАМЫСЕЛ ИЗОБРЕТАЕТ ЗАНОВО

| Пункт замысла | Что уже есть |
|---|---|
| «глобальный текстовый дескрипшен вещи» | **`TechCard.concept`** — «concept (design intent)», textarea на HEADER, 2000 симв., печатается на листе `description` тех-пака (внутренний скоуп) |
| «CONSTRUCTION DESCRIPTION» | **`TechCard.details[]`** — `DetailsEditor` на HEADER, блоки key+text+медиа |
| «описание для каждой фотки» | **`TechCardMediaItem.caption`** — есть на проводе, есть в БД (`VARCHAR(255)`), **UI нет нигде**. В схеме подписано `// carried (v2; no UI yet)` |
| «роль картинки front/back/collar» | **`TechCardMediaKind`**: FRONT, BACK, DETAIL, LINING, PREVIEW, MOODBOARD, REFERENCE, SWATCH. Не хватает ровно одного значения — **SIDE** |
| «CONFLICTS TO RESOLVE» | **`AnalyzeTechCardConstruction`** — на проде. Категория `question`, severity, refs, верификация якорей, dismiss, «file as issue» |
| «NEEDS YOUR INPUT» | **`GetTechCardReadiness`** — 9 серверных ключей: style_number, size_range, bom_fabric, costing, costing_computes, colorway_linked, lab_dip, signoffs, construction_graph |
| «CONFIRMED» | **Sign-off** — 7 секций, `signed_digest`, детект устаревания, «EDITED AFTER SIGN-OFF» на бумаге |
| «нам нужен вектор» | `renderLayoutSvg` — **написан, ноль вызовов**. DXF R12 writer — работает в проде |
| «серверная генерация картинки» | `FileStore.UploadContentImage(ctx, rawB64, folder, name)` — внутрипроцессный метод, прецедент в `betaseed/media.go` |
| «асинхронные задания» | 12 тикер-воркеров + аутбокс `send_email_request` + `command_idempotency` |
| «3D-вьюер» | `three@0.161` **уже в зависимостях** admin-client |

**Вывод:** пункт 1 замысла («референсы с ролями и текстом») на 90% уже в схеме. Работа — не новая
модель, а UI для `caption` + одно значение энума.

### Чего нет вообще

* **Ни одной картиночной модели.** `chatMessage.Content` в Go — простая строка, картинку модели
  послать НЕЛЬЗЯ. Мультимодальный вход — новая работа.
* **Никакого учёта денег.** Ни поля, ни таблицы. Это нормально при $0.01/вызов и опасно при $0.30.
* **Провенанса на прозаических полях нет.** `consumption_source`, `wastage_source`, `price_source`,
  marker `source` — только числовые/денежные, и все НАМЕРЕННО вне отпечатков.
* Модель по умолчанию — **`anthropic/claude-sonnet-5`**, не opus-5: `OPENROUTER_MODEL` не задан ни
  на бете, ни на проде, значит константа в коде — то, на чём всё реально работает.

## 2. ГДЕ ЗАМЫСЕЛ РЕЖЕТ ПРОТИВ ЗЕРНА КОДОВОЙ БАЗЫ

### 2.1 Ничто, написанное моделью, не сохраняется сервером

Оба живых AI-пути держат это правило: `AnalyzeTechCardConstruction` не пишет НИЧЕГО (находки живут в
`sessionStorage`), `GenerateTechCardOperations` возвращает черновик, сохраняет человек.

`UpdateTechCard` — **полная замена документа** с оптимистичной блокировкой. Асинхронная джоба,
дописывающая карточку после того, как у оператора снят снимок формы, будет **молча затёрта следующим
сохранением**. Это ровно класс дефекта «черновик стирает отсутствующие поля», уже пойманный.

**Единственный безопасный путь:** генерация возвращает кандидата → открытый клиент применяет его в
состояние формы обычными сеттерами → человек сохраняет обычным путём. Плюс серверная проверка
`frozen` **в момент применения**, потому что `<fieldset disabled>` глушит только клик и фокус —
программный `setValue` из колбэка проходит насквозь.

### 2.2 «CONFIRMED» ≠ подписано

Замысел говорит: подтверждённые детали печатаются в тех-паке. Это создало бы **фабричный контент,
не покрытый ни одной проекцией и ни одной подписью**, при том что вся машина построена на обратном:
что печатается → читается из полей карточки → поля покрыты проекцией секции → подпись штампуется
против дайджеста.

**Правило:** подтверждение решения = обычная правка обычного поля через обычную форму. Запись решения
— это ПРОВЕНАНС, а не источник печати. Иначе получается третий механизм одобрения рядом с sign-off и
release-гейтом, и единственный не подключённый к релизу.

Побочно: назвать корзину «CONFIRMED» опасно, в продукте уже есть «approved». Правильное имя —
**Accepted decisions**, и рядом с каждым пунктом показывать состояние подписи покрывающей секции.

### 2.3 Стежок принадлежит ОПЕРАЦИИ, а не кисти

`tech_card_operation` уже несёт `seam_class`, `machine_type`, `needle_count`, `needle_gauge_mm`,
`stitches_per_cm`, `row_spacing_mm`, `topstitch_rows`. Кисть со своим полем «coverstitch» — это
**вторая истина о конструкции внутри DESIGN-артефакта**, то есть ровно [[false-split-dictionaries]],
который уже документирован как класс.

**Правило:** штрих ССЫЛАЕТСЯ на операцию (`operation_ref`, nullable — флэт рисуют рано, операции
пишут поздно), внешний вид ВЫВОДИТСЯ из полей операции. Несвязанный штрих допустим как чистая
графика; сверка «штрих ↔ операция» становится проверкой покрытия.

Цена честная: **связи «операция ↔ ребро геометрии» сегодня нет.** `tech_card_operation_piece` — это
`(operation_id, piece_id, display_order)`, целые детали, никогда рёбра. Это новое моделирование — и
самая ценная новая связь во всей системе (см. §5).

### 2.4 Ткань и цвет должны приходить из BOM и колорвеев

Свободный выбор «цвет + тип ткани» в рендере рисует ткань, которой нет в закупке. Запрос рендера
обязан выбирать: принятый лист + существующий колорвей + существующая BOM-статья ткани + опционально
свотч. Результат — иллюстративное медиа: **никаких выносок, не в релиз-готовности, не в фабричном паке.**

### 2.5 Отпечаток DESIGN

`designProjection` = `{concept, media(id/kind/caption/category), callouts, details}`.

Отсюда механически следует:
* принятие сгенерированного флэта → **DESIGN протухает**;
* правка подписи референса → DESIGN протухает;
* применение сгенерированного concept/details → DESIGN протухает;
* реимпорт SVG рождает новый media id → DESIGN протухает.

Это НЕ баг — это честное поведение. Но: **любое новое поле обязано входить в проекцию условной
хвостовой парой** ([[digest-tail-pairs-not-positions]]), иначе сам факт деплоя протухает каждую
подписанную карточку в базе. И метаданные генерации (модель, промпт, сид, хеши входов) остаются
**вне** дайджеста — так уже сделано для `price_source`.

**Живая дыра, найденная попутно:** клиентский пред-сейв `SECTION_WATCH_FIELDS` для DESIGN
**не содержит `concept`**, а серверная проекция содержит (`signoffs-field.tsx:50` против
`techcard_section_digest.go:272`). Сегодня это редко ловится; автозаполнение concept сделает это
регулярным — экран не предупредит, протухание вылезет после сохранения. Чинить до фичи.

## 3. ПЕРЕГЕНЕРАЦИЯ: ЧЕСТНЫЙ ОТВЕТ

«Перегенерить, сохранив артефакты» означает разное для разных слоёв.

| Слой | Сохраняется? |
|---|---|
| Текст выноски, номер, связь с деталью | **Да, всегда.** Номера уже резервируются, пока на них ссылаются |
| **Позиции выносок, растр → растр** | **Нет. Точка.** Между двумя сэмплами генеративной модели нет соответствия. Правильное поведение — то, что код уже делает: убить геометрию, оставить точку. Плюс нужен **список на перестановку**: каждая осиротевшая выноска с миниатюрой старого контекста |
| Позиции, **вектор-диффом** | Да, условно — если перегенерация ограничена «модель правит предыдущий SVG» и id элементов выживают. Это ЕДИНСТВЕННЫЙ механизм, при котором обещание честно, и он диктует архитектуру |
| Человеческие правки вектора под перегенерацией | **Отказать или форкнуть, никогда не мержить.** Автомерж, который никто не может проверить, = молчаливое уничтожение работы |
| Тканевые рендеры | Определить артефакты ПРОЧЬ: рендер не принимает выносок вовсе. Тогда «сохранить» = «дизайн пережил смену ткани», а это надежда на качество модели, а не свойство системы |
| **Отказать всегда** | перегенерация на замороженной карточке (проверять НА СЕРВЕРЕ в момент применения); перегенерация технического листа, когда ниже уже висят выкройки/раскрой/лоты — без явного «отцепить производственные ссылки» |

## 4. ФИСИБИЛИТИ: ЧЕМ РИСУЕТСЯ ФЛЭТ

### 4.1 Растр → автотрейс: владелец прав, и 2026 это не починил

Дефект структурный. Potrace, VTracer, Illustrator Image Trace, Vectorizer.AI, Recraft vectorize —
все **обводят контур**, а не восстанавливают осевую линию. Следствия:

* линия толщиной 0.5pt становится **длинной тонкой залитой щепкой с двумя сторонами**;
* толщина обводки перестаёт существовать как атрибут — менять нечего;
* `stroke-dasharray` неприменим → отстрочка как редактируемая сущность умирает;
* **пунктирная отстрочка — худший случай**: каждый штрих трассируется отдельной замкнутой кляксой.
  200 мм строчки с шагом 3 мм = ~60 несвязанных фигур;
* масштабирование ломает чертёж: «обводка» масштабируется вместе с фигурой.

Centerline-трассировка существует (Inkscape, autotrace `-centerline`), но нестабильна на переменной
толщине и даёт открытые полилинии, не кривые. **Ничто в 2026 не решает это надёжно.** Ранг: последний.

### 4.2 LLM пишет SVG напрямую: только мелкие символы

Бенчмарк SVGenius (arXiv 2506.03139, 22 модели): image-to-SVG PSS у Claude-3.7 падает 23.70 → 15.47
easy→hard, у GPT-4o 23.43 → 11.67 (теряет половину). Названные режимы отказа — структурные ошибки,
неточность координат, ошибки слоёв. Флэт по числу узлов — твёрдо «hard».

Где реально работает: легенда стежков, диаграмма класса шва по ISO 4916, символ фурнитуры — **20–80
узлов, не 800**.

### 4.3 Нативная векторная генерация — спайк на один вечер

**Recraft V4.1 Pro Vector есть на OpenRouter: $0.30/картинка, ~15 с, вход до 1 референса, выход SVG.**
Композирует путями, а не трассирует. Независимые замеры: ~80–90% чистоты рисунка от руки при
~20–30% лишних узлов. Плюс Recraft `/styles` — стиль строится из **1–10 референсных картинок**.

**А у вас есть корпус собственных флэтов, нарисованных в Illustrator.** Скормить их `/styles` и
генерить в своём фирменном стиле — эксперимент на один вечер, ключ уже есть.

### 4.4 Параметрические блоки + LLM-параметризация — единственный путь к «как от руки»

Именно к этому сошлось исследовательское поле, что и есть сильнейший аргумент:

* **NGL** (arXiv 2602.20700, май 2026) — DSL на 44 параметра, **без обучения**: картинка + схема →
  GPT-5 → валидация → детерминированная конвертация в GarmentCode. Chamfer 1.75 против 3.99 у
  ChatGarment, **0% отказов**.
* **ChatGarment** (CVPR 2025) специально ужал конфиг с 900 до 350 токенов ради стабильности.
  Урок однозначный: **меньше схема — выше надёжность.**
* GarmentCode — **MIT**.

Почему только это удовлетворяет реальным требованиям:
* «три вида в одном масштабе на общей базовой линии» — тривиально (три прохода рендера над одним
  набором параметров). Ни одна картиночная модель этого не гарантирует;
* **стабильные id элементов** (`front__pocket_welt__L`) → выноска якорится на ЭЛЕМЕНТ, а не на долю
  кадра. Единственный вариант, где перегенерация и аннотация уживаются;
* качество Illustrator-уровня, потому что пути рисовал человек;
* стоимость — один текстовый вызов (~$0.05), 5–15 с, влезает в текущие 60 с.

Цена честная и большая: **блоки должен кто-то нарисовать.** Параметризованный блок = 1–3
дизайнер-дня + работа рендерера, и библиотека И ЕСТЬ продукт. Жизнеспособно только потому, что
GRBPWR маленький и повторяет силуэты: 10–20 блоков вероятно покрывают линию. За пределы своего
пространства не обобщается — NGL говорит это прямо.

### 4.5 Вывести флэт из DXF — практически мертво

Выкройка — это ПАНЕЛИ; тех-рисунок — СОБРАННАЯ вещь в плоской проекции. Для конвертации нужна
**топология швов** (какое ребро с каким сшито), а DXF её не несёт. Проверено в НАШЕМ дереве:
в `PieceDTO` есть `poly`, `inner[]`, `grain[]` и **ничего на уровне рёбер**; грепы `piece_edge` /
`edge_id` / `segment_id` по `internal/entity` и всем 328 миграциям дают ноль. Слой 14 в живых
выгрузках — линия шва НА ОДНОЙ детали (см. [[dxf-layers-real-files]]), а не отношение между двумя.
Плюс весь DXF-конвейер — **клиентский TypeScript** (~7.2k строк), на сервере его нет.

> ⚠️ Отдельное утверждение «стандарт ASTM D6673 отозван в 2019 без замены» из первого черновика
> **отозвано как непроверенное** (агент признал фабрикацию цитаты). Вывод не меняется — он держится
> на замере нашего собственного дерева выше, а не на стандарте.

## 5. КРУГЛЫЙ РЕЙС ЧЕРЕЗ ILLUSTRATOR — самое трудное требование в брифе

Тяжелее самой генерации. Документированное поведение:

* **`data-*` атрибуты выбрасываются.** Adobe сломал это в Illustrator 28.5+ (`data-name` больше не
  экспортируется), открытый тикет в UserVoice.
* **Пользовательские XML-неймспейсы уничтожаются.** Это убивает приём Ink/Stitch
  (`xmlns:inkstitch=…`, параметры на путях) — он работает потому, что **Inkscape** сохраняет
  неизвестные неймспейсы. Illustrator — нет.
* `<desc>`, `<metadata>` — выбрасываются.
* `id` выживают **условно**: экспорт должен стоять в Object IDs = Layer Names; пробелы становятся
  подчёркиваниями; **дублирующиеся имена слоёв получают случайный хеш-суффикс**; CC 2019+ срезает
  часть имён, которые CC 2018 сохранял; пустые группы молча удаляются.
* `stroke-dasharray` **выживает** как настоящая пунктирная обводка.
* `<marker>`, `pattern` на обводке, `pathLength` — считать потерянными.

**Отсюда контракт:**
1. Никакие метаданные приложения не едут «в теле». Ни `data-*`, ни неймспейс, ни `<desc>`.
2. Единственный носитель — **сама строка `id` / имени слоя**, потому что человек в Illustrator видит
   её в панели слоёв и имеет причину не переименовывать. **Формат id обязан быть
   `[A-Za-z][A-Za-z0-9-]*` и ничего больше.** Illustrator экранирует: пробел → `_`,
   **подчёркивание → `_x5F_`**, запятая → `_x2C_`, ведущая цифра → префикс `_3`, дубликат имени →
   длинный числовой хеш в конце. Если в id нет ни пробелов, ни подчёркиваний, ни запятых, ни
   ведущих цифр — экранировщик становится **пустой операцией** и id возвращается байт-в-байт.
   (Живой пример из реального экспорта: слой `center, top, leading: 235 pt` вернулся как
   `center_x2C__top_x2C__leading:_235_pt_00000142166234487451118750000006251493092934391439_`.)
   Прототип прежней рекомендации `seam__01JB…__coverstitch` **неверен** — двойное подчёркивание
   превратится в `_x5F__x5F_`. Правильно: `seam01JB4KcoverstitchA` или дефисы: `seam-01JB4K-cover`.
3. **Серверный сайдкар по этому токену.** Вернувшийся SVG — только геометрия; всё остальное
   склеивается по id. Всё, что не сматчилось на возврате, — новая геометрия без метаданных;
   **показать это, а не угадывать.**
4. **Круглый рейс переживают только осевые линии.** Запечённое украшение стежка — производный вывод,
   перегенерировать на импорте, никогда не парсить обратно. Экспортировать в отдельную явно
   названную группу слоёв, чтобы дизайнер знал, что она одноразовая.
5. Считать каждый рейс потерей и **диффать**: сколько id потеряно, добавлено, задублировано.
   Молчание здесь — это [[stale-remote-ref-hides-parallel-session]] заново.

### И отдельно: стежок в SVG

| Стежок | Механизм | Работает декларативно? |
|---|---|---|
| Локстич 301 сплошной | обычная обводка | да |
| Отстрочка (пунктир) | `stroke-dasharray` | да |
| Двухигольный / коверлок | **2–3 параллельных смещённых пути** | нужна генерируемая геометрия |
| Зигзаг | ресэмплированная полилиния ±амплитуда | нужна геометрия |
| Оверлок / флэтлок 607 | повторяющийся глиф вдоль пути | нужна геометрия |

`<marker>` не помогает: `marker-mid` срабатывает только на существующих вершинах пути — на кривой
Безье из 4 узлов вы получите 2 маркера, а не 40 стежков.

Где наивный подход рушится:
* **Масштаб.** `stroke-dasharray` в пользовательских единицах: зум ×2 удваивает штрих. Стежок —
  физические 3 мм. Сегодняшний код это уже показывает: `shapes.tsx` хардкодит `strokeDasharray='3 3'`
  в экранных единицах и `vector-effect: non-scaling-stroke` — верно для аннотации, неверно для стежка.
  **А координаты аннотаций — безразмерные доли 0..1 без физического масштаба вообще.**
* **Углы.** Штрих может лечь поперёк острого угла. У настоящей строчки в углу — прокол иглы.
* **Замкнутые пути.** Шаг пунктира почти никогда не делится нацело на замкнутый контур: последний
  штрих сталкивается с первым.
* **Параллельное смещение не бесплатно.** Смещение кубической Безье не даёт кубическую Безье.
  `geom/offset.ts` (418 строк) — **замкнутый Минковский-оффсет наружу для припуска**, не оффсет
  открытой полилинии. Машинерия переиспользуема, функция — нет.

Реалистичная оценка редактора со стежками и круглым рейсом: **6–10 недель**, и это самый рискованный
пункт всего брифа.

## 6. ТКАНЕВЫЙ РЕНДЕР

Самый лёгкий пункт брифа и самый вероятный «вау». Всё нужное — на OpenRouter, тот же ключ.

**Но одношаговое «скормить флэт Nano Banana и получить вещь» НЕ удержит геометрию.** Это не провал
промптинга. Бенчмарк Simple-V2V (arXiv 2605.12271, май 2026), ось sketch-following из 100:

| Модель | Общий | Цвет | Счёт | **Скетч** | **Поза** |
|---|---|---|---|---|---|
| GPT Image 2 | 64.7 | 92.4 | 91.8 | **34.0** | 20.0 |
| Seedream 5.0 Lite | 58.4 | 68.7 | 88.8 | **32.4** | 16.8 |
| Nano Banana 2 | 51.4 | 69.7 | 67.1 | **22.3** | 19.1 |

И BFL пишет это в собственной документации: *«Expecting pixel-perfect structural matching — FLUX.2
interprets structure semantically»*. Выделенные ControlNet-эндпоинты у фронтира **удалены**
(`flux-pro-1.0-canny` отдаёт 404).

Фэшн-специфично, GarmentSketch (arXiv 2606.14025): *«Nano Banana даёт очень реалистичные картинки,
но часто отходит от точной структуры скетча; ControlNet и T2I-Adapter, наоборот, сохраняют форму, но
не дотягивают по фотореализму»*.

### Что из этого следует — два этапа, разные модели

1. **Геометрия — настоящий control-адаптер.** ControlNet не умер, он мигрировал в открытые модели.
   Лучший: **Z-Image Turbo + Fun-Controlnet-Union-2.1**, Apache-2.0 с обеих сторон, обновлён
   02.2026, **MLSD + canny подходят под прямые швы и жёсткие края панелей**, **$0.0065/MP** на fal,
   опубликована развёртка conditioning scale. Хостед-альтернатива под задачу:
   **Bria FIBO `sketch_to_colored_image`, $0.04**, обучена только на лицензированных данных.
2. **Материал и свет — нативная edit-модель со свотчем как референсом.** Google документирует этот
   приём дословно: *«используя приложенный набросок как структуру и приложенный образец ткани как
   текстуру…»*. До 14 референсов у Gemini 3.1 Flash, 8–10 у FLUX.2 с привязкой цвета к hex.
3. **Колорвеи — Ideogram `colorways`** (до 4 масок, hex на маску, заявлено сохранение геометрии,
   материалов, принтов и теней) и **`material-swap`** (свотч как материал-референс, заявлено
   сохранение силуэта, конструкции, **швов** и затенения). Цены не опубликованы.

### «Перегенерить, сохранив» — что сохранимо

Сохранимо: силуэт и класс вещи (гонять флэт референсом каждый раз); идентичность объекта
(Nano Banana Pro документирует до 6 объектных картинок); характер ткани (флис против шармёза читается
хорошо); цвет — примерно, с проверкой сэмплом пикселя.

**Не сохранимо, и не обещать:** точные позиции швов, число строчек, ритм пунктира, расположение
фурнитуры; точный цвет между прогонами (никто не гарантирует ΔE); что угодно измеримое;
детерминизм — **у Gemini и OpenAI сида в API нет вообще** (у FLUX.2 есть).

**Единственный стабильный «именованный ручник» — обученный артефакт, и он дёшев:**
fal Qwen Image Trainer **$2.00/1k шагов**, fal FLUX.2 **Edit** Trainer **$11.82/1k шагов** — он
учится на ПАРАХ `_start`/`_end`. Если есть архив флэтов, спаренных с готовой съёмкой, это
supervised-модель «флэт → фото» за ~$12.

**И честная оговорка: драпировка.** Ни у одной модели здесь нет ручки на то, как падает тяжёлый
флис против шармёза. Оптика (блеск, переплетение) адресуема, механика — нет.

## 7. НАСТОЯЩЕЕ 3D

**Не генерировать.** Два факта решают вопрос.

**Факт 1 — юридический, и он жёсткий.** Открытые веса Hunyuan3D лицензированы с территориальным
исключением; строка 3 файла лицензии: *«THIS LICENSE AGREEMENT DOES NOT APPLY IN THE EUROPEAN UNION,
UNITED KINGDOM AND SOUTH KOREA»*. GRBPWR — **UK Ltd**. Веса вам не лицензированы вовсе.

**Факт 2 — структурный.** Почти все image→3D модели полевые (SDF/occupancy) и не умеют открытую
поверхность: вещь выходит **водонепроницаемой двухслойной кляксой**. Исключение ровно одно —
**Microsoft TRELLIS.2** (MIT, 12.2025), которая называет случай прямо: *«✅ Open Surfaces (e.g.,
clothing)»*; ~3 с @512³ на H100, нужно ≥24 ГБ VRAM и Linux. Но и по ней AnySurf (05.2026) пишет, что
результаты «всё ещё содержат ошибки нормалей и топологии».

**Что делать вместо.** `three@0.161` уже в зависимостях; `<model-viewer>` — **72.6 КБ**, Apache-2.0,
турнтейбл и камера из коробки, а React 19 полностью поддерживает кастомные элементы, так что обёртка
не нужна. Добавить роль `.glb` в библиотеку файлов и **попросить внешнего конструктора, который и так
делает вам DXF, выгружать `.glb` рядом**. Ноль генерации, ноль AI, **2–3 дня**, настоящая сшитая вещь.

Ловушка при этом одна и её надо знать: в glTF 2.0 `doubleSided` **по умолчанию `false`**. Вещь —
тонкая оболочка; если экспортёр не выставит флаг, изнанка, видимая через горловину и проймы,
отрендерится **дырами**.

Если когда-нибудь захочется автоматизации: у CLO3D есть публичный портал разработчика
(developer.clo3d.com), **822 функции**, SDK v11.0.0 от 08.2026, и в нём буквально весь конвейер —
`ImportDXF` → `AddSeamlinePairGroup` → `Simulate` → `ExportGLB`. Но: Windows/macOS, headless — платный
отдельный SKU, и **публичная документация сама себе противоречит** (на headless-микросайте
`Simulate` и `AddSeamlinePairGroup` ОТСУТСТВУЮТ). Спрашивать у CLO напрямую, прежде чем закладывать.

И главное: **вывести шитьё из DXF нельзя** (см. §4.5). Швы придётся авторить один раз на стиль и
хранить у себя как `(pieceA, edgeA, pieceB, edgeB, dirA, dirB)`. Это представление ложится напрямую
в `AddSeamlinePairGroup` у CLO и в `stitches` у GarmentCode (обе сигнатуры проверены); про Browzwear
и Blender как цели переносимости — **не проверено, из плана убрано**.

## 8. «REVIEW & OPEN DECISIONS» — что тут реально новое

Как экран — на 80% федерация уже существующего:

* **CONFLICTS TO RESOLVE** = находки Analyze (категория `question`). Есть, с якорями, категориями,
  severity, дельтой между прогонами, идентичностью `sha256(category ‖ sorted(refs))` (заголовок
  НАМЕРЕННО исключён, чтобы перефразировка не теряла триаж) и «file as issue».
* **NEEDS YOUR INPUT** = 9 серверных release-блокеров, уже с привязкой к вкладке.
* **CONFIRMED** = sign-off по секциям с дайджестами.

**Реально новое — ровно две корзины: PROPOSED ASSUMPTIONS и SUGGESTED PROPOSALS**, и только если
у них есть ДОЛГОВЕЧНОЕ состояние. Сегодня dismissal живёт в `sessionStorage` и умирает с вкладкой.

Заявленные корзины смешивают ТИП и СОСТОЯНИЕ. Правильно две оси:
* **тип**: conflict | assumption | proposal
* **состояние**: open | accepted | rejected | superseded
* **производное**: stale — потому что основание изменилось

Минимальная запись решения: стабильный id · тип · секция sign-off · текущая формулировка ·
человеческая замена · стабильные refs на обсуждаемые факты · **дайджест основания по этим refs** ·
каноническое назначение (`concept` | `detail:collar` | операция) · идентичность кандидата из
(тип + назначение + отсортированные refs) · состояние · источник (человек / машинная проверка /
прогон модели) · аудит.

Поведение при изменении карточки: пересчитать дайджест основания; refs исчезли или дайджест изменился
→ **stale, обратно в «нужен просмотр»**; историю принятия сохранить; назначение изменилось независимо
→ superseded. **Дайджест СЕКЦИИ здесь слишком груб** — правка BOM не должна инвалидировать решение
про воротник; нужен пофактовый.

При повторном прогоне: не дублировать уже отслеживаемое; **не переписывать человеческую формулировку**;
не закрывать решение только потому, что модель его в этот раз не упомянула; отклонённый кандидат
остаётся подавленным, пока факты-основания существенно не изменятся.

## 9. ЧЕГО В СПИСКЕ НЕТ, А НАДО (ранжировано по ценность/усилие)

1. **POM / таблица мерок, вычисленная из DXF + проверка градации.** Без AI вообще. Есть геометрия по
   размерам, есть примитив `dim` — двухточечный замер. POM это ровно «две именованные точки на
   детали, измеренные по размерам». Детерминированно, проверяемо, **фабрично-обращено** — то, чем
   сгенерированный флэт не станет никогда. Лучшее ценность/усилие в списке с большим отрывом.
2. **Канонический PDF релиза (Ф7).** У замороженного релиза должен быть замороженный документ.
   `window.print()` не гарантирует, что два человека получат одинаковый файл. Рендерить из снапшота
   релиза, хранить SHA-256, ЭТО отдавать фабрике. Ценнее, чем рендеры и 3D вместе взятые.
3. **`.glb` вьюер + попросить файл у конструктора.** 2–3 дня, настоящее 3D.
4. **Автозаполнение concept / details.** Они это и просят; самый дешёвый настоящий выигрыш, чистый
   текст, влезает в существующий синхронный эндпоинт, никакой новой инфраструктуры.
5. **Стабильная идентичность выноски.** Номер не должен быть первичным ключом производственной
   ссылки. Неизменяемый ключ + номер как представление. До миграции — серверный отчёт о зависимостях
   и атомарная команда перед любым удалением/перенумерацией/заменой медиа.
6. **Предпросмотр последствий сохранения/релиза.** Какие подписи протухнут, какие выноски сбросятся,
   какие детали/операции/дефекты ссылаются на затронутые номера. Сегодня дайджест говорит «что-то
   изменилось», но не «что». С AI-авторингом без этого протухание подписей будет казаться произволом.
7. **Матрица сквозной прослеживаемости.** Строка на деталь кроя: DXF по размерам → BOM-ткань по
   колорвею → дублирование → входы/выходы сборки → покрытие операциями → покрытие настилом.
   Данные уже есть; нет читаемого ответа на «где эта деталь перестаёт быть специфицированной».
8. **Примерка → набор правок ревизии.** Ценный AI-сценарий: превратить свидетельства примерки в
   контролируемый change set (мерки, деталь, правка конструкции, операция, закрытие дефекта).
9. **Критика списка операций вместо генерации.** `GenerateTechCardOperations` уже собирает полный
   контекст карточки и каталог работ. Развернуть его — «чего не хватает, что дублируется, что
   расходится с каталогом» — мелкая правка против известной проблемы (79% прод-операций неразличимы).
10. **Проверка SMV на вменяемость** против медианы каталога. Не генерация, а сравнение.

**Пункты 1, 2, 4, 5 и 9 выше по ценность/усилие, чем всё в исходном брифе, кроме автозаполнения описания.**

## 10. СПИСОК НА УБОЙ

1. **Сгенерированные «внутренние» флэты, несущие производственные выноски.** Требовать явного
   повышения до принятого листа — либо аннотации остаются приватными и ненумерованными.
2. **Произвольная фотография → чистый редактируемый вектор как общая способность.** Либо честный
   растр для понимания, либо ограниченный генератор по шаблонам. Достоверной середины нет.
3. **Полноценный векторный редактор в браузере.** Наращивать 2352-строчную аннотационную поверхность
   до мини-Illustrator — портить работающий инструмент. Круглый рейс + узкие оверлеи, привязанные к
   операциям; тяжёлая геометрия — в Illustrator.
4. **Кисти, хранящие собственный тип стежка.** Штрих ссылается на операцию, вид выводится.
5. **Свободный выбор цвета и типа ткани в рендере.** Только из BOM-статей, колорвеев и свотчей.
6. **Рендер как свидетельство драпировки, посадки или технологичности.** Это иллюстрация.
7. **Генерируемое вращаемое 3D.** Плюс отдельно: открытые веса Hunyuan3D в UK/EU **не лицензированы**.
8. **Автоматическое сохранение чего угодно сгенерированного.** Кандидат → дифф → Apply человеком →
   обычный save.
9. **Монолитная таблица решений, копирующая в себя release-блокеры и находки Analyze.**
10. **Печать подтверждённой формулировки вне дайджеста секции.**
11. **Сохранение геометрии выносок сквозь кроп, перегенерацию или реимпорт SVG.**
12. **Отдельная вкладка «AI» или визард.** Ручной путь остаётся главным; действие AI живёт рядом с
    тем самым артефактом, который оно предлагает изменить.

## 11. ЧЕСТНЫЙ MVP

4–6 недель, один разработчик + немного дизайнерского времени.

1. **`generation_job`** + 13-й тикер-воркер, скопированный с `internal/mail/worker.go` (тикер +
   `context.WithTimeout` + `saferun.Recover` + бэкофф 30 с → 5 мин + `health.Reporter`;
   `send_email_request` — работающий образец claim-and-mark аутбокса). Писать
   `total_cost` из OpenRouter `/generation` в строку джобы, месячный жёсткий потолок. Переиспользовать
   `internal/circuitbreaker`. Клейм — коротким отдельным стейтментом, не внутри длинной транзакции
   (пишущие транзакции SERIALIZABLE). **3–5 дней.**
2. **UI для `caption`** на плитке медиа + значение энума **`TECH_CARD_MEDIA_KIND_SIDE`**. Это и есть
   пункт 1 замысла; остальное уже в схеме.
3. **«Generate flat»**: вход — уже размеченные медиа + описание; выход — **растровый** флэт обычной
   строкой медиа, неизменяемой, версионированной. Nano Banana Pro ~$0.13 или Nano Banana 2 ~$0.067.
4. **Аннотировать СУЩЕСТВУЮЩЕЙ поверхностью.** Ноль новых систем координат, ноль нового редактора.
   Выноски прикалываются к новому `media_id` и не могут «съехать», потому что медиа append-only.
5. **Автозаполнение concept / details** на существующем синхронном эндпоинте — как кандидат, который
   человек применяет и сохраняет. Перед этим починить дыру `SECTION_WATCH_FIELDS` (§2.5).
6. **Спайк параллельно, на этой неделе:** Recraft V4.1 Pro Vector на OpenRouter ($0.30, ~15 с) +
   собрать Recraft `/styles` из своих рисованных флэтов. Один вечер и несколько долларов решают,
   жизнеспособен ли нативный вектор. Если да — добавить **«скачать SVG»** как экспорт, а не как
   редактируемый объект в приложении.

**Явно НЕ в MVP:** векторный редактор, кисти-стежки, тканевый рендер, 3D, параметрическая библиотека.

**Почему такая форма.** Четыре живые привычки (рисуем в Illustrator, иногда CLO, просто фотографии
вместо чертежа, снимок бумажного эскиза) уже сводятся к «картинка в строке медиа, которую кто-то
аннотирует». Генерация встаёт **пятым источником того же артефакта**, а не новой подсистемой. Ничего
не надо заменять, ничто новое не может разъехаться, и если команда фичу проигнорирует — потеряно
шесть недель, а не шесть месяцев.

Фаза 2 решается по факту: если сгенерированные флэты реально аннотируют — строить параметрическую
библиотеку (§4.4), единственный путь к Illustrator-качеству со стабильной идентичностью. Если на них
посмотрели один раз и забыли — ответ получен, и векторный редактор не построен.

## 12. ИНФОРМАЦИОННАЯ АРХИТЕКТУРА — где спорят критики

Единственное место, где два независимых критика разошлись.

**Fable:** ноль новых вкладок. Референсы с ролями → moodboard; генерация и вектор → sketch;
рендеры → записи в галерее эскиза с отдельным kind; автозаполнение → в поля, которые оно заполняет;
review → не в DESIGN вообще. Отдельная вкладка «AI» институционализирует проблему двух источников
истины.

**Codex:** три вкладки вместо трёх — **Brief** (идентичность, concept, аспекты описания
конструкции) · **References** (сырые картинки, теги вида/аспекта, подписи) · **Flats** (рабочие
кандидаты, принятые листы, круглый рейс SVG, нумерованные выноски). AI — действие внутри Brief и
Flats, не вкладка. Review — межсекционный, в бэнд SPEC перед sign-off.

Оба согласны в главном: **AI не вкладка, а действие рядом с артефактом**. Расходятся только в том,
переезжает ли блок `concept`/`details` с HEADER в отдельный «Brief». Это ровно то, что должен решить
прототип — два варианта на одном экране.

Технические факты для этого решения:
* `sketch` и `moodboard` — ОДИН компонент, обе смонтированы одновременно, делят ОДИН массив
  `callouts` и одну историю отката;
* нумерация ПО-ЛИСТОВАЯ и асимметричная: `referencedNumbers()` возвращает `[]` для мудборда.
  Слить листы = схлопнуть два независимых пространства номеров, и заметка на мудборде начнёт двигать
  номера эскиза, из которых сервер выводит ИМЯ детали кроя;
* `notes` пишется из ДВУХ вкладок сразу (header + moodboard);
* никакой внешний компонент не диплинкует в header/moodboard/sketch — снаружи ссылаются только на
  `?tab=samples`. Так что перестановка внутри бэнда дешёвая;
* `IDEA_TABS` хардкодит `['header','sketch','moodboard','samples','history']`;
* удаление вкладки — решённый приём: алиас в `FOLDED_TABS`, старая ссылка продолжает работать.

## 13. ЗАМЕРЫ И ЛОВУШКИ, ПОЛУЧЕННЫЕ ПОЗЖЕ (проверено инструментально)

Отдельный агент прогнал potrace 1.16 + ImageMagick 7.1.2 на синтетическом «тех-рисунке»
(1200×800, **5 авторских путей**, из них 2 отстрочки `stroke-dasharray="14 9"`) и прочитал исходники
autotrace, Inkscape и багтрекер Adobe. Числа ниже — замеренные, не оценочные.

### 13.1 Автотрейс: цена в цифрах

| | авторский SVG | potrace по умолчанию |
|---|---|---|
| байт | **473** | **10 099** (×21) |
| рисуемых элементов | **5** | **83 `<path>`** (×17) |
| якорей | **12** | **398** (×33) |
| атрибутов `id` | 5 | **0** |
| объявлений обводки | 5 (`stroke-width:3`) | **0** — выход `fill:#000; stroke:none` |
| семантика пунктира | 2 × `stroke-dasharray` | **0** — 80 из 84 контуров это отдельные штрихи |

Примитивы поштучно: прямая линия (2 якоря) → **4 якоря замкнутого контура**; кубическая Безье
(2 якоря) → **14** (×7); окружность → **2 концентрических контура, 28 якорей**, идентичность
«окружность» потеряна.

**Отстрочка, одна линия 900 px:**

| шаг пунктира | сколько отдельных замкнутых контуров | якорей |
|---|---|---|
| `14 9` | **40** | 160 |
| `8 6` (частый стежок) | **65** | 260 |

Это **×80 по якорям и ×40 по объектам** против одного пунктирного пути. И фильтры мелочи
(potrace `--turdsize`, VTracer `filter-speckle`) в другую сторону **удаляют короткие штрихи как
мусор**. Толщина линии не спасает: 1 px → 333 якоря, 3 px → 398, **6 px → 624**.

Непрерывность: G1 держится (83–100% стыков), **G2 нет вообще** — на трассированной окружности
r=300 скачок кривизны на стыках: медиана 160%, максимум 200%; локальный радиус гуляет
2 860 → 18 050 при истинном 3 000. Выглядит круглым, редактируется отвратительно.

**Единственные два инструмента с настоящей осевой линией:** autotrace/Inkscape (**но
`src/output-svg.c` физически не печатает `stroke-width` — ни разу во всём файле**, так что толщина
теряется всегда) и **Illustrator Image Trace в режиме `strokes`** с `maxStrokeWeight` (0.01–100) и
`minStrokeLength` (по умолчанию 20 px). Vectorizer.AI говорит прямо: *«We do not currently support
centerline tracing, so all stroked geometry gets represented as narrow filled shapes.»*

### 13.2 Почему структурированный промежуточный формат, а не сырой SVG

Самое чистое контролируемое доказательство — CAD-Recode: **одна и та же GPT-4o**, одна и та же
геометрия, три представления:

| представление | точность понимания |
|---|---|
| **CadQuery Python-код** | **76.5%** |
| командная последовательность CAD | 63.2% |
| сырое облако точек | 42.3% |

**+13.3 пункта за программу против собственного командного формата при неизменной модели.**

И решающее для нас — **правка существующего SVG моделью**:

| задача | результат |
|---|---|
| Vector-Bench: хирургическая правка сырого SVG (34 эндпоинта, 1360 запросов) | **2.35% полного успеха, 54% валидного SVG, 37.8% обрыва** |
| VCG-Bench: правка структурированного диаграммного XML | **0.998–0.999 успеха исполнения** (Gemini-3-Pro, GPT-5.2) |

Названные режимы отказа при правке SVG: буквальная частичная правка; **глобальные переписывания,
ломающие ссылки и переставляющие элементы**; изменение защищённых объектов. Только **19.85**%
запросов сохранили незатронутое содержимое.

Первичная генерация мелкого SVG при этом валидна почти всегда (GPT-4o и Grok-4 — 100% render success
на коротких задачах). **Проблема не в первом кадре, а в масштабе и в мутации.**

SVGenius определяет «hard» как **16 путей / 1149 контрольных точек**; реальная графика — 500–1000
путей. Деградация начинается уже на 16.

**Вывод, который это диктует архитектуре:** модель НИКОГДА не правит наш SVG напрямую. Модель
выдаёт/правит **структуру**, приложение детерминированно рендерит SVG. Это же снимает вопрос
стабильных id — их минтит рендерер.

### 13.3 Illustrator: пять конкретных ловушек

1. **`<defs>` обязан идти ДО ссылок на него.** Иначе Illustrator **не импортирует вообще ничего** —
   при полностью валидном SVG. Однострочная правка на нашем писателе, снимает режим тотального отказа.
2. **`stroke-dasharray` ограничен ШЕСТЬЮ значениями.** В панели Stroke ровно 3 поля штриха и 3 поля
   пробела; восьмизначный `24,10,6,10,6,10,6,10` рендерится **сплошной линией**, правильно
   отображаясь везде остальном. Значит любой стежок, закодированный пунктиром, обязан влезать в
   ≤6 значений: `4 2`, `0 3`+round cap, `6 2 1 2` — годятся.
3. **`<marker>` мёртв дважды.** По спецификации `marker-mid` рисуется только на вершинах пути:
   кубическая Безье — ОДИН сегмент, значит одна вершина; дуга `A` на 350° — **ноль промежуточных
   маркеров**. А в Illustrator баг с 2019 года (подтверждён вплоть до 25.4.1, 25 голосов, без
   резолюции Adobe): при `marker-end` **исчезает сам путь**, остаётся только стрелка.
4. **«Align dashes to corners» уничтожает идентичность объекта.** Админ Adobe дословно: *«When it's
   on, Illustrator internally treats this stroke exactly like you have in the SVG — a group of normal
   dashed lines with recalculated gaps and dashes.»* Один прямоугольник превращается в N безымянных
   фрагментов в `<g>`, и `id` пропадает. Детектировать и отклонять.
5. **«Preserve Illustrator Editing Capabilities» — это теневая копия, а не метаданные.** Вшивает
   целый AI-документ в base64 внутрь `<i:pgf>` (410 КБ против 3 КБ на той же графике). При
   переоткрытии Illustrator читает свой приватный payload, а **не наш SVG-DOM** — то есть правки,
   сделанные приложением, молча выбрасываются. Держать ВЫКЛЮЧЕННЫМ.

Дополнительно подтверждено потерянным на импорте: `vector-effect` (не поддерживается),
`pathLength` (нет соответствующего понятия), `<title>`, `<desc>` (перестал писаться с 26.3.1),
`class` на `<g>`, CSS в `<style>` (пути приходят без обводок вовсе — **писать презентационные
атрибуты, не `<style>`**). Глубина вложенности растёт на уровень за каждый круг.

**Инструкция дизайнеру (записать и выдать):** Export As SVG (не Save As) · Object IDs = **Layer
Names** · Minify **off** · Preserve Illustrator Editing Capabilities **off** · «align dashes to
corners» **off** · Style = **Presentation Attributes** (по умолчанию стоит инлайновый `style=`).
И пиниться на конкретную версию Illustrator: поведение id менялось в ТОЧЕЧНЫХ релизах в обе стороны
(23.x, 26.1, 26.2, 26.3.1, 27.1, 27.2, 28.2, 28.5, 28.6).

**Проверенный прототип на практике — ai2html от New York Times**: вся конфигурация едет в **именах
слоёв и артбордов** с двоеточным синтаксисом (`Layer1:svg`, `Artboard1:600,fixed`), и ни один
SVG-атрибут не обязан выжить. Коммерческий CAD→SVG конвертер (CADViewer) пишет одно и то же
**трижды** — в `id`, в `class` и в собственный неймспейс. Избыточность и есть урок.

### 13.4 Стежки: что реально доступно

* **Пунктир (≤6 значений) — единственный механизм, доживающий до Illustrator живой обводкой.**
  Покрывает локстич, смёточный, точки проколов, pick stitch.
* **Зигзаг, оверлок, коверлок, флэтлок, двухигольный — примитива в SVG нет.** Либо 2–3 наложенных
  пунктирных обводки (придут в Illustrator как N независимых путей), либо **запечённая
  ресэмплированная геометрия** — ровно то, что делают Ink/Stitch, libembroidery и pyembroidery:
  `d = "M" + …` по одной вершине на прокол иглы.
* **Изящный ответ — `marker-pattern` / `marker-knockout-left|right` из SVG Markers Level 1** —
  Editor's Draft от 14.09.2025, **ноль реализаций**. В планы не закладывать.
* **`<hatch>` из SVG 2 отложен в будущую версию**, `stroke-linejoin: arcs` и `miter-clip` описаны, но
  нигде не реализованы.
* **Замкнутый путь: пунктир не заворачивается.** Спецификация сбрасывает узор в начале каждого
  подпути, никакого wrap-around; последний штрих упирается в первый торцами. Чинится `pathLength`
  (`pathLength="120" stroke-dasharray="1 1"` = ровно 60 стежков на любом контуре) — но
  **Illustrator `pathLength` не поддерживает**, значит для экспорта нужен пересчёт
  `getTotalLength()` и округление числа периодов.
* **Углы пунктир не видит вовсе** — пробел может лечь на угол и стереть его. Алгоритм-решение есть
  готовый: Inkscape Dashed Stroke LPE, режимы «Use segments» (каждый сегмент получает целое число
  штрихов, поэтому граница всегда попадает на угол) и «Half start/end».
* Ink/Stitch держит **~140+ атрибутов в неймспейсе `http://inkstitch.org/namespace`** — и это
  подтверждает §5: приём работает потому, что **Inkscape** сохраняет чужие неймспейсы. Дирк Шульце
  из Adobe прямо описывает, что Illustrator понимает только фолбэк и осиротляет расширения.

### 13.5 Что это меняет в плане

1. **§4.1 подтверждён замером, а не мнением.** Автотрейс закрыт окончательно.
2. **Появился шестой пункт в MVP-контракт писателя SVG:** `<defs>` первым, id в алфавите
   `[A-Za-z][A-Za-z0-9-]*`, презентационные атрибуты вместо `<style>`, пунктир ≤6 значений,
   ноль `<marker>`, ноль `vector-effect`, ноль `pathLength` в экспортном профиле.
3. **Модель не правит SVG. Никогда.** 2.35% против 99.8% — это не тюнинг промпта, это выбор
   архитектуры. Структура → детерминированный рендер.
4. **Стежок сложнее пунктира = запечённая геометрия в отдельном одноразовом слое**, который на
   импорте перегенерируется, а не парсится обратно.
